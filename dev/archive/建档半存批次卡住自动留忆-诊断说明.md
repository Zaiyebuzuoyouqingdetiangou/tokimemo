# 建档批次「半存」后，每一楼的自动建档都秒失败 · 诊断说明（给接手的 AI）

基线：0.99.90 / r84.158-test-upkeep（插件代码与 r84.157 相同）。**已在 r84.159 修复（见 CHANGELOG）**，本文件只作记录。更正：用户没有点「先将成功分段入档」；半存批次来自插件在非自动建档失败后自动入档成功分块（`archive/repository.js` 的 `autoCommitCompletedArchiveChunks`）。开工前先读 `dev/PROJECT.md`。

## 1. 用户现场（2026-09-27，TT / Tauri，r84.157）

诊断报告 recentTasks 里有两条：

| 顺序 | 结果 | 要点 |
|---|---|---|
| 较早 | `RMT_JSON_NOT_FOUND` | 3 个分块，前 2 块成功；第 3 块请求挂了约 686 秒，返回 128 字、finish_reason=stop，不是 JSON。同时酒馆弹「后端错误：The request timed out before the target service responded」（用户的代理 `:3000`） |
| 最近 | `RMT_RECOVERY_INPUT_CHANGED` | 353 ms，0 次请求，recovery.phase=initialization，category=chat，有 archiveBudget |

截图里档案整理草稿一栏：标题「重试未完成分块」，仍建议「先将成功分段入档」。

## 2. 第一条：不是插件的错

代理超时后，返回的东西不是 JSON，按设计判 `RMT_JSON_NOT_FOUND`，不自动重试，保留成功的 2 块。686 秒远超 360 秒上限，是因为超时只按页面可见时间计（`core/requestTaskCenter.js` 的 `runGenerationRequestWithTimeout`），手机切到后台的时间不算。诊断里本次建档请求的输出预算是 120000 token，可以建议用户把最大输出调低再试。

## 3. 第二条：插件的错（已在测试环境复现）

复现步骤（`tools/runtime-harness.mjs`，bundle 模式；要用 `setMemorySourceLedgerBackendForTests` 把账本换成假的，否则会碰 IndexedDB）：

1. 已有档案。自动每楼窗口建档一次，3 块里第 3 块失败 → 留下 segments 草稿（已完成 2 块）。
2. 点「先将成功分段入档（不生成）」→ 成功。档案里的 `archiveImportProgress` 变成 `nextBatch 0、partialParts [0,1]`，并带 `archivePartialDraft`。草稿栏看起来和之前一样（仍是「重试未完成分块」，仍建议先入档）。
3. 聊天多一楼，下一楼到点自动建档 → **立即失败**，code / phase / category / 0 请求都与用户诊断一致。之后每一楼都一样。

原因：`archive/importOperation.js`

- 第 105 行：取到档案里未完成的批次后，比对身份时已用 `ignoreChatFingerprint: floorWindowSync` 放过整段聊天指纹（r84.154）。
- 第 313 行（以及循环里第 362、382 行）：`assertBatchCommitIdentity(context, { progress })` 又比了一次。此时 `progress.taskInputV1` 是这次刚捕获的（第 311 行覆盖），`progress.identity` 是旧批次的，聊天指纹必然不同 → `changedInput('chat')`。这几处没有像第 105 行那样放过每楼窗口建档。

同一状态下还有两个问题：

- 聊天多了一楼后点「重试未完成分块」：会**先发出付费请求**，再在第 564–566 行（`receiptBase?.archivePartialDraft && !floorWindowSync` 时比整段聊天指纹）拒绝保存。钱花了，结果不存。
- 「放弃整理草稿」解不开：它只清草稿，档案里半存的批次还在，下一楼照样失败。

## 4. 用户现在能怎么办（未改代码）

测试环境里验证过：点「按当前条件另起任务」可以解开。它会重新整理没入档的部分和新的楼（要花请求），完成后下一楼自动建档恢复正常。

## 5. 修法方向（待用户同意后单独出包）

原则同 r84.157：每楼自动建档接着做档案里的旧批次时，旧批次的来源是它自己记下的那些楼（批次清单里每个片段都有哈希，`resolveBatchParts` 会逐片核对），聊天后面新增的楼不算变化。要改的点：

1. 第 313 / 362 / 382 行：对 `floorWindowSync` 接旧批次的情况，身份比对同样不比整段聊天指纹（其余字段照比）；来源是否变了交给 `resolveBatchParts` 的逐片哈希。
2. 第 564–566 行：先想清楚「重试未完成分块」（非自动）在聊天变长后该怎么办。至少要在**发请求前**就判断能不能存，不能先花钱再拒绝。
3. 顺带：半存之后草稿栏不该再建议「先将成功分段入档」。

必须加的测试：半存 + 下一楼自动建档成功；半存 + 旧批次里的楼被改仍失败；手动路径行为不变；聊天变长后「重试未完成分块」不会先发请求再拒绝。
