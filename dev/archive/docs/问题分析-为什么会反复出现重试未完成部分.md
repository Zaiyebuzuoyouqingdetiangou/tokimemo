# 为什么会反复出现「重试未完成部分」

这是 2026-09-22 的原因记录。已做和未做的清单在 `施工方案.md`。下面关于「3000 / 3200 会压低输出上限」和「横幅只写任务尚未完成」的句子，以后文更正为准。字数下限没有放宽。

截图里的「春 · 已保留 0 个成功分段」和按钮「重试未完成部分」，对应的是角色互动里「春」这一页的未完成草稿。文案「任务尚未完成」不是模型原文，是界面在草稿上找不到整本失败码时用的兜底句。

## 结论

不是设置里那个「自动重试 1–5 次」造成的。那个开关默认关，而且只在一次已经失败之后才会再排队。第一次出现这张横幅，发生在自动重试之前。

也不是插件在后台把同一段无限重请求。每个分段内部最多自动再请求 1 次（一共 2 次尝试），而且只针对标明可重试的 JSON 错误、校验错误和限流。超时、鉴权、配额、上下文超限、连接结果不明的失败不会自动再打一次。

会让人觉得「要重试很多次」的，是同一页一次次没有留下成功分段，横幅就一直留着。点一次「重试未完成部分」就再花一次生成额度。春这一页本身就要先写 Voice，再写 Scenario；Voice 没写成时 Scenario 不会发，成功分段就是 0。

提示词是失败的原因之一，但不是这张横幅每次出现的唯一原因。

## 这张横幅实际在说什么

界面把分段状态是 `retry` 的行算成「失败段」。只要失败段大于 0，或者整本草稿上有失败码，就会给出「重试未完成部分」。

「任务尚未完成」这六个字只在整本草稿没有 `failureCode` 时出现。分段自己身上的失败码不会写进这句。所以横幅可以在两种情况下长得一模一样：

1. 请求发出之前，恢复层会先记一条 `state: 'retry'` 的分段，用来冻结这次的请求配方。如果这时刷新、关掉页面，或请求没走到写入整本失败码，草稿里就是「0 个成功分段」加这条占位分段。横幅已经会出现，但模型可能还没返回正文。
2. 模型确实失败了，失败码写在分段上，之后整本的 `failureCode` 被清掉（例如后来有一段被标成完成时会清空整本失败码）。横幅仍显示兜底句，看不到「没有完整 JSON」或「疑似被截断」。

因此，单凭这张截图不能断定是提示词写坏了。要区分的话，得看任务中心或导出草稿里这一段自己的 `failureCode`。

## 提示词和输出合同会让同一页反复失败

春的生成不是一次请求写完整季。代码里是两段：

- Voice：提示词要求只返回 1 个 `kind=spring` 的 Voice Drama，`script` 5～10 句、总文本不少于 280 个汉字，并且「只输出 JSON」。这一段请求上限是 3000 tokens。
- Scenario：再要求 1 个小事件，6～12 句、不少于 360 个汉字，上限 3200 tokens。

模型只要出现下面任一种，这一段就不算成功，页面就继续停在「重试未完成部分」：

- 回了散文、解释或代码围栏外的说明，正文里没有完整 JSON 对象（`RMT_JSON_NOT_FOUND`）。
- JSON 有开头但没有闭合（`RMT_JSON_TRUNCATED`）。这种会走「继续生成」，按钮文案不是「重试未完成部分」。截图上的按钮是重试，所以这次保存下来的草稿没有被归成截断续写。
- JSON 能解析，但台词句数或字数不够本地校验。校验失败默认 `retryable: true`，内部还会自动再请求那 1 次；两次都不过，就留给手动重试。
- 最终正文是空的，或只有推理没有最终 JSON。

这些都是「提示词要求一份完整、够长的 JSON，而模型这一次没交出来」。提高全局最大输出不一定有用：这两段用的是自己的 3000 / 3200 上限，不是设置里的全局输出上限。

角色互动的其他页也是同类合同，只是长度不同。例如萤火虫要求每颗光点 5～10 句、约 140～420 字，而且要一次交出多颗。越长、越严，越容易在同一页上反复看到重试。

## 哪些不是这次的原因

- 设置「失败后自动重试未完成部分」：默认关闭。打开后默认再试 1 次，最多 5 次，而且不会重试超限草稿，也不会重试「继续生成」那种截断草稿。它不会制造「春 · 0 个成功分段」的第一张横幅。
- 分段内部自动重试：最多 1 次额外请求，不是用户要点很多次的那个按钮。
- 输入预算默认 6 万：超预算会在发送前拦住，并给出预算错误，不会伪装成「任务尚未完成」。
- 「另起任务前的草稿仍保留」是另一条建档草稿提示，不会请求模型，也不是春这一页的重试次数。

## 已拍板（这一轮按这个做，字数下限不动）

- 他的房间、角色互动春夏秋冬、私人终端、回忆相簿、结局路线、ADV 事件索引：第一次格式合法就标完成。旁边写「可以第二次生成」具体内容（对白和描述 / 小事件 / 各应用正文 / 共同回忆 / 路线正文 / 事件正文）。设置里「第一次完成后，自动进行第二次生成」默认关。前世今生和蝴蝶效应的后段依赖前一段，拆开后页面还不能读，所以仍一次做完。
- 空回整段重来一次。写到一半没闭合的，自动接着补，不丢掉已写内容。
- 任务中心失败行写具体原因，不再把成功的第一次写成「没有新的可保存分段」。
- 提示词改成短任务说明、编号规则、文末只输出一个 JSON。各页原有字数下限和字段校验保持不变。

## 优化方案

这一节是当时的方案。第 3 条「放宽字数下限」没有做。已经写进代码的是：提示词改成短合同，下限和字段校验保持原样。

先修正上面的一处过时说法：角色互动各段代码里的 3000 / 3200 已经不再拿去压低供应商的输出上限。现在真正发给模型的最大输出，是设置里的那一个输出上限。所以上限设得很小，确实会把 JSON 截断；上限已经够大时，再加大它，解决不了「回了散文」或「句数不够」。

反复要点「重试未完成部分」，主要是因为这一次没有留下成功分段。要提高一次交卷的比例，按下面的顺序做，收益从大到小。

1. 把输出合同放到提示词的最前和最后，中间才是创作要求。最后三行固定成：只输出一个 JSON 对象；第一个字符必须是 `{`，最后一个字符必须是 `}`；不要前言、解释、引用或代码围栏。现在「只输出 JSON」埋在长要求的末尾，模型更容易先写说明。
2. 给每一页附一个最短合法例子，字段名和层数与校验用的完全一致，例子里的正文用占位短句，不把创作要求写进例子。模型有样可抄时，少把正文写成散文。
3. 放宽「差一点就算整段失败」。春的 Voice 现在要 5～10 句且不少于 280 字，Scenario 要 6～12 句且不少于 360 字。JSON 能解析、只是少一句或少几十字，现在整段失败，页面就停在 0 个成功分段。可以改成：结构合法就先收下，字数或句数不足只记一条可补写原因，按钮走「继续生成」，不要走「重试未完成部分」。
4. 手动重试时带上上一轮失败原因。分段内部那一次自动重试已经会加「上一轮你返回的是散文」。用户点的「重试未完成部分」如果仍按冻结的原提示词重发，模型会再交一份同样的散文。重试正文前应加上具体失败码：没有完整 JSON、没有闭合、句数不够，或字数不够。
5. 严格 JSON 的那一段把温度降到 0.3～0.4。角色互动 Voice / Scenario 现在是 0.65，更容易在 JSON 外面加说明。叙事可以靠提示词里的场景要求，不必靠高温度。
6. 春这一页继续保持 Voice 和 Scenario 分两次请求，但第一次只要求能闭合的短剧本（例如 4～6 句）。过了本地校验再允许加长。现在一次就要写满下限，模型写到一半更容易断在未闭合的 JSON 上。
7. 不要把「逐字抄锚点」和「写满一整段对白」放进同一个对象里要求同时满足。锚点抄不对会被丢掉，对白写不满也会整段失败，两件事叠在一次请求里，失败面最大。能拆开的页，先交结构，再交对白。
8. 失败码写到任务行上。现在整本失败码被清掉之后，界面只剩「任务尚未完成」，看不出是散文、截断还是字数不够，重试也无从对症。这是显示问题，不是再请求一次就能变准。

不建议把「失败后自动重试」默认打开来掩盖准确率。那只是多花额度重发同一份容易失败的合同。也不建议把所有页合成一次超长请求：页越长，越容易在闭合括号之前被截断。
