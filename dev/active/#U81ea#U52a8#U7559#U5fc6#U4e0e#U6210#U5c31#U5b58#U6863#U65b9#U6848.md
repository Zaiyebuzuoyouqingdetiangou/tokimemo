# 自动留忆与成就存档方案

> 本文是产品逻辑与不可违背规则的主文档，不作为逐文件施工 List。  
> 逐模块请求顺序、次数和完成判据见 [自动留忆模块生成合同.md](./自动留忆模块生成合同.md)。  
> 依赖顺序、文件落点和勾选式任务清单见 [自动留忆实施清单.md](./自动留忆实施清单.md)。

文档职责：

- 本文决定“用户会经历什么、什么算完整、数据如何归属、失败时怎么表现”；
- 模块生成合同决定“抽中后具体跑哪些步骤、何时允许揭晓”；
- 实施清单决定“开发先后顺序和每轮完成门槛”；
- 实施清单不得自行修改本文的产品决定；发现冲突时先回到本文拍板。

## 1. 结论

方案可行，建议在现有建档、自动更新、生成队列、成就库和聊天 metadata 存储能力上整合实现，不另建一套生成系统。

目标流程：

> 设置 API → 选择单人卡／多人卡 → 建档并排除不喜欢的模块 → 可选首次排队生成 → 每固定 N 楼增量建档判断 → 从允许模块中随机抽签 → 完整生成一份回忆与一个成就 → Toast、悬浮信封和楼层尾部提示 → 回忆与成就长期留档 → 从成就跳回原剧情楼层。

## 2. 已确认的产品决定

1. 自动抽签的对象是用户勾选的**内容模块**，不是随机抽一段聊天。
2. 存储采用混合模式：
   - 聊天 `chatMetadata` 是正式主档；
   - IndexedDB 只作为身份绑定的恢复备份；
   - API Key、自动检查点和轻量全局索引继续使用各自现有的安全存储。
3. 生成完成后同时提供：
   - Toast 提醒；
   - 酒馆页面悬浮信封；
   - 最新楼层正文尾部的插件入口。
4. 楼层尾部入口只挂载 DOM，不修改 `message.mes`，不会随正文发给模型。
5. 每次**成功生成一份新的真实回忆**后生成一个对应成就。
6. 如果本轮没有归档出可验证的新 Mxxx，则记为“没有形成新回忆”，不伪造回忆或成就。
7. 自动间隔默认 5 楼，允许用户设置 1～1000 楼；模块抽签仍是随机的，楼层间隔本身不随机。
8. 每个固定周期分为“增量建档判断”和“模块完整生成”两阶段。前者通常一次请求；后者按模块实际合同可能包含一次或多次请求。
9. 一个成就对应一份**完整模块成果**，不是一次底层 API 请求。终端等模块即使需要两次或更多请求，全部完成后也只对应一个成就。
10. 模块局部成功时保留成果和恢复状态，但只显示“回忆生成中”，不出现信封、不解锁成就。
11. 成就与模块结果放在该模块最后一次生成响应中，不额外调用成就 API。
12. 成就底层区分“历史成就”和“收藏成就”，界面仍统一展示为成就：
    - 历史成就证明聊天剧情中确实发生过的里程碑；
    - 收藏成就证明一份推演／未来／番外模块成果已经完整生成，不表示其中剧情已经发生。
13. 正常流程不增加成就请求；若组合响应中的成就缺失或校验失败，保留模块成果和外置待补状态，只有用户明确确认后才发送一次小型成就修复请求。

## 3. 现有能力

当前项目已经具备：

- 每个模块独立设置的按楼层自动更新，默认间隔 20 楼；
- 自动任务检查点、跨页面任务锁和失败后等待下一间隔；
- 单人卡／多人角色卡选择；
- 从世界书选择多人卡人物、手动补充人物、随机加入一人和选择群像；
- 最多 5 个逻辑生成任务、2 个 provider 请求并发；
- 后台生成、切页后继续和原聊天／原档案版本写回保护；
- 正式 Mxxx 档案及 `messageStart`／`messageEnd` 楼层范围；
- 带真实 `sourceMemoryIds` 和 `sourceMemoryAnchor` 的成就库；
- 聊天 metadata 主档、gzip 派生缓存和 IndexedDB 独立备份；
- 部分模块的合并生成能力。

本功能主要工作是增加统一启用流程、随机调度、揭晓交互和成就溯源，不是重写上述基础设施。

## 4. 使用流程

### 4.1 首次启用

1. 设置并检查独立 API。
2. 选择卡片类型：
   - 单人卡：沿用当前角色卡身份；
   - 多人卡：从世界书或手动名单中选择人物。
3. 选择聊天读取范围及现有记忆来源。
4. 展示全部支持自动生成的模块。每个模块必须写明：
   - 生成什么内容；
   - 属于真实回忆、设定推演还是未来／番外；
   - 一次完整成果通常需要多少次 API；
   - 可能因内容量产生的请求范围；
   - 完成后会保存在哪里。
5. 所有模块在偏好界面中默认选中，用户可以排除不喜欢的模块；运行时只有已完成“自动计划、完整成果判定、成就末包”适配的模块才进入抽签候选，尚未适配的模块必须明确标为暂不可自动生成。
6. 选择自动检查间隔，默认 5 楼，可在 1～1000 楼内调整。
7. 创建当前聊天档案。
8. 询问是否立即进行第一次生成：
   - 可以多选模块后排队生成；
   - 也可以全部跳过，只完成建档；
   - 跳过不会关闭以后按楼层自动抽签。
9. 显示预计请求次数、可能包含的多段请求及费用提示。
10. 用户确认后才把首次勾选模块加入统一任务队列。

首次生成与自动抽签模块池应分开保存。例如用户可以首次生成房间和私人终端，但只允许相簿、邮箱、日历进入日常自动抽签。

### 4.2 首次排队生成

- 用户的一次明确确认可以授权已勾选模块进入队列。
- 队列继续遵守最多 5 个逻辑任务和 2 个 provider 请求并发。
- 各模块保留自己的 Prompt、校验、局部成功保存及失败恢复逻辑。
- 已成功模块不能因其他模块失败而回滚。
- 多阶段模块必须在确认页显示“可能包含多次 API 请求”，不能把一个逻辑任务描述为一次请求。
- 自动生图不进入本流程；图片仍由用户明确点击并确认。
- 用户可以跳过全部首次生成；此时只保存档案、模块池和自动间隔。
- 每个首次生成模块全部完成后分别形成一份回忆与一个成就；底层多次请求不拆成多个成就。

### 4.3 自动抽签

自动留忆使用统一的固定楼层周期。用户设置 `intervalFloors`，默认 5，允许范围 1～1000。每个模块不再拥有彼此独立的自动计数器。

每轮流程：

1. 保存 `nextDueFloor = lastCompletedFloor + intervalFloors`。
2. 刷新、切页和重复消息事件只读取该检查点，不重复开始本轮。
3. 到达 `nextDueFloor` 后，第一阶段执行增量建档与剧情重要性判断。短增量通常只需一次请求，但会按聊天约 30000 字符、外部记忆约 26000 字符分段，不能把这一阶段写死为一次请求：
   - 从新增楼层提取真实 Mxxx；
   - 标记其中的重要剧情；
   - 不单独增加逐楼分类 API。
4. 如果没有形成任何新 Mxxx，本轮记为 `noop`：
   - 不发送模块生成请求；
   - 不生成信封或成就；
   - 从当前检查完成楼层开始计算下一周期。
5. 如果产生新 Mxxx，先计算当前真正可生成的模块候选池，再执行随机抽签。
6. 请求前持久化本轮抽签票据，刷新和重试必须复用同一个模块，不能重新抽签规避失败。
7. 第二阶段完整生成该模块：
   - 轻量模块通常一次请求；
   - 终端等多阶段模块按现有合同执行两次或更多请求；
   - 第一请求若只产生目录、索引或生成计划，它只能算中间状态；
   - 系统必须按照本轮计划自动继续请求，直到目录中的全部 App、事件、路线、条目或其他必需正文完成，不要求用户再次点击；
   - 已完成阶段立即安全保存，但该模块的本轮完整计划全部完成前不算一份回忆。
8. 模块最后一次响应同时返回成就数据，不额外发送成就请求。
9. 模块与成就均通过校验并保存后，才建立揭晓记录并显示信封。
10. 从本次完成楼层重新计算下一个固定周期，避免短时间连续生成。
11. 失败时保留同一抽签票据和局部成功结果，只补未完成部分，不自动换模块。

“整体完成”指抽签后冻结的**本轮有限计划全部完成**，不是要求填满一个可以无限增长的永久内容库。例如：

- 电话先生成 App 目录，再自动完成目录中的全部 App；
- ADV 先生成事件索引，再自动完成本轮索引中的全部事件正文；
- 结局先生成路线目录，再自动完成本轮全部可用路线正文；
- 相簿先生成条目索引，再自动完成关系快照和全部已解锁条目的评论；
- 蝴蝶效应完成 MAIN、本轮全部分支、Ω 及本轮要求的正文；
- 前世今生完成引子、全部卷宗、今生回响和落款。

本轮计划一旦持久化，后续新增聊天不会在任务中途无限扩大它；新增内容由下一次周期处理。当前计划未完成时，不开始下一轮抽签。

固定间隔用于决定何时检查，随机数只用于选择模块，不作为数据身份。持久化记录至少包含：

```text
version
enabled
allowedModes
excludedModes
intervalFloors
lastSuccessFloor
nextDueFloor
drawnMode
drawId
status
archiveRevision
createdAt
updatedAt
```

## 5. 自动模块池

### 5.1 用户控制

用户可以：

- 勾选允许自动抽签的模块；
- 随时排除不喜欢的模块；
- 暂停自动留忆；
- 在 1～1000 之间修改固定楼层间隔；
- 查看当前抽中的模块及下一次到期楼层；
- 手动重新抽签，但必须再次确认可能产生请求；
- 保留手动生成所有模块的能力。

### 5.2 模块分级

首次向导和设置页共用同一份模块说明注册表。所有支持自动运行的模块默认勾选，用户可在建档时或以后任意取消、恢复。界面应区分：

- 单请求或较轻模块；
- 可能多段请求的模块；
- 明确偏未来模拟／番外的模块；
- 不适合自动执行的生图操作。

请求次数必须写成真实可理解的值或范围，例如“通常 1 次”“目录 1 次 + 每个 App 1 次”“最少 2 次，缺项重试另计”，不能把一个逻辑任务统一写成“一次生成”。

未来模拟模块即使进入抽签，也不能用其虚构内容解锁真实历史成就。成就只能引用本轮新增的正式 Mxxx。

### 5.3 参考 toto 的抽签策略

只复用抽签原则，不复制 toto 的主题／展现形式领域模型：

1. 先硬排除用户取消勾选、当前不可生成和本轮不适用的模块。
2. 近期抽中过的模块降低权重，但不永久禁用。
3. 长期符合资格却没有抽中的模块逐步增加权重，避免小模块长期饿死。
4. 用户以后可设置喜欢／不喜欢；喜欢只提高权重，不绕过禁用、证据和完成条件。
5. 使用 `crypto.getRandomValues()`，受限 WebView 中再兼容回退 `Math.random()`。
6. 抽签结果在请求前持久化；失败、刷新和恢复都复用原抽签结果。
7. 候选池为空时安全 `noop`，不恢复用户明确排除的模块。

## 6. 新回忆信封

### 6.0 生成中的外置壳

从模块抽签完成到整份成果保存之前，酒馆页面显示类似兔子镜的独立生成壳，但不依赖或修改兔子镜：

- 显示“回忆正常生成中”；
- 多阶段模块显示安全进度，例如“私人终端 1/2”；
- 关闭插件主窗口后仍可看到任务状态；
- 不显示 Prompt、API 返回原文或私密证据；
- 局部成功不提前显示信封和成就；
- 失败后显示可恢复状态，重试只补未完成部分。

### 6.1 单份结果、多个入口

一次成功生成建立一条统一的揭晓记录：

```text
id
drawId
mode
title
createdAt
triggerFloor
chatId
archiveRevision
sourceMemoryIds
achievementIds
revealState
targetMessageIndex
```

Toast、悬浮信封和楼层尾部按钮都只引用该记录 ID，不复制正文。

### 6.2 Toast

成功保存后显示简短提示：

> 今天留下了新的回忆。

Toast 不显示私密正文、Prompt、证据锚点或 API 返回原文。点击 Toast 可打开信封。

### 6.3 悬浮信封

- 挂载在酒馆页面，由本插件独立控制；
- 不依赖兔子镜或其他插件；
- 显示未拆封／已拆封状态；
- 点击后播放轻量拆信动画并打开回忆卡；
- 切换聊天后只显示当前聊天的待揭晓内容；
- 历史聊天中的已揭晓回忆仍可从插件档案查看。

### 6.4 楼层尾部入口

- 优先挂载在生成完成时最新的角色消息楼层；
- 只增加插件 DOM，不改写聊天消息对象；
- 不进入后续模型上下文；
- 聊天重新渲染后，根据 metadata 中的揭晓记录重新挂载；
- 两个入口打开同一份回忆；
- 找不到目标 DOM 时不阻止保存，只保留悬浮信封和 Toast。

## 7. 成就系统

### 7.1 生成规则

- 每份完整生成并保存的新回忆对应一个 API 生成的成就。
- 成就数量按完整模块成果计算，不按底层 API 请求数计算。
- 成就分为：
  - `historical`：真实历史成就，描述由本轮新增 Mxxx 直接证明的关系或剧情里程碑；
  - `collection`：收藏成就，表示对应模块成果已经完整生成，不能写成模块中的推演剧情已经真实发生。
- 两类成就都保存对应模块成果 ID，并尽可能引用本轮新增 Mxxx 作为创作来源和正文跳转依据。
- 成就名称、说明和解锁条件可以由模型创作。
- `sourceMemoryIds`、楼层范围和时期不能只相信模型，应由本地档案重新解析。
- 没有有效 Mxxx 时不能生成 `historical` 成就。
- 未来模拟、平行世界、后日谈和人设推演只能生成 `collection` 成就，不能自动解锁真实历史成就。
- 两类成就在界面中统一进入成就库，但必须用短标签或说明让用户能看出“剧情里程碑”与“作品收藏”的差异。

### 7.2 请求合并

成就必须作为本轮模块**最后一次生成响应**中的独立输出区，不额外调用成就 API：

```json
{
  "moduleResult": {},
  "achievement": {}
}
```

模块结果和成就分别校验、分别保存：

- 模块成功、成就失败：保留模块，成就进入待补；外置壳继续显示“回忆已完成 · 成就待补”，暂不显示最终信封；
- 成就成功、模块失败：不单独公布该成就，等待模块结果完成；
- 保存失败：保留已校验成果，提供只重试保存；
- 不为了成就失败重做已成功的模块正文。

多阶段模块把成就放在最后一个已有请求中。若该模块当前无法在不改坏恢复合同的情况下加入成就输出，则该模块不能先进入自动抽签池，必须完成适配后再开放，不能静默增加第三次成就请求。

若最后响应中的成就字段缺失或校验失败：

1. 已成功模块成果原样保留，不重做正文；
2. 不自动发送额外请求；
3. 外置壳显示安全的“成就待补”状态；
4. 用户明确点击“补写成就”并确认费用后，才发送一次只包含模块摘要、成就类型和受控 Mxxx 证据的小型修复请求；
5. 修复成功并保存后再建立最终揭晓记录和信封。

### 7.3 成就回看

成就卡增加：

- 成就名称；
- 解锁条件；
- 解锁时间；
- 对应时期；
- 关联回忆标题；
- 楼层范围；
- “查看回忆”；
- “跳到原剧情”。

时期、标题和楼层由 `sourceMemoryIds` 查回正式档案后本地生成，避免模型写错。

### 7.4 跳转楼层

1. 从成就的 `sourceMemoryIds` 读取关联 Mxxx。
2. 合并取得最早 `messageStart` 和最晚 `messageEnd`。
3. 关闭或收起插件窗口。
4. 将一基楼号转换为宿主消息索引。
5. 找到当前已渲染的消息节点并滚动到起始楼。
6. 对对应楼层范围作短暂高亮。

如果来源来自外部摘要、继承档案或没有正文楼层：

- 显示来源说明和 Mxxx 内容；
- 不提供虚假的楼层跳转。

如果目标楼层当前没有渲染：

- 明确提示“目标楼层尚未加载”；
- 不模拟点击第三方插件或读取宿主私有数据库；
- 保留楼号和档案内回看入口。

## 8. 存储设计

### 8.1 聊天主档

继续使用现有：

- `heartbeatMemoriesArchiveV3`：正式 Mxxx 档案；
- `heartbeatMemoriesTheaterV3`：压缩后的派生内容、信封、成就和自动计划。

这样档案随聊天保存，在同一服务器／聊天文件可用时，酒馆和 TT 能读取同一份内容。

### 8.2 本机恢复备份

继续使用 IndexedDB 独立备份，但定位保持为：

- 保存失败后的恢复来源；
- 源聊天暂时不可读时的身份匹配只读副本；
- 不作为另一份可独立修改的主档；
- 不自动绑定到其他聊天；
- 清站点数据、换设备或浏览器不会自动同步。

### 8.3 不进入聊天正文的数据

以下内容不得写入 `message.mes`：

- 信封入口；
- 成就卡；
- 插件 UI 状态；
- 自动调度检查点；
- API 配置与密钥；
- 生成诊断。

## 9. SillyTavern 与 TT 兼容性

### 9.1 SillyTavern

单角色聊天可基于现有扩展 API 实现。

“多人卡”指一张角色卡内包含多个人物，并由用户选择人物名单。当前代码明确拒绝 `groupId`，因此不等于 SillyTavern 原生群聊。

原生群聊需要单独处理：

- 多角色卡槽身份；
- 群聊消息说话人；
- 群聊 chatId 和写回作用域；
- 多头像和成就归属；
- 当前全部 `currentCharacterGuard()` 约束。

本方案不顺带宣称支持原生群聊。

### 9.2 TT

聊天 metadata、插件界面、任务队列和恢复备份原则上可复用。

需要真机确认：

1. `navigator.locks` 是否可用；
2. `localStorage`、IndexedDB、CompressionStream 是否可用；
3. 聊天消息 DOM 和 `mesid` 是否与酒馆一致；
4. 页面重挂载后楼尾入口能否恢复；
5. TT 安全区、返回手势和窄屏触摸目标；
6. 后台切页、切聊天和 WebView 暂停后的任务状态。

如果 TT 缺少 Web Locks，可增加 IndexedDB 原子租约作为安全后备；不能使用无法保证互斥的普通 localStorage 假锁。没有安全锁时继续保持现有行为：自动任务停用，手动功能可用。

## 10. 失败与恢复

- 档案同步失败：不抽模块，不生成成就。
- 没有新 Mxxx：本轮 `noop`，不伪造内容。
- 模块失败：保留档案、同一抽签票据和局部成功内容；外置壳显示未完成，后续只补缺项。
- 成就失败：保留模块成果，成就标记待补；不自动请求，用户确认后才执行小型成就修复。
- chatId、角色、人物名单或 `archiveRevision` 变化：拒绝旧结果写回。
- 信封 UI 挂载失败：内容仍已保存，可从档案打开。
- 楼层跳转失败：显示楼号，不影响成就和回忆阅读。
- metadata 保存失败：保留已确认的本机恢复结果，不显示“已经永久保存”。

## 12. 验收标准

1. 用户能完整走通首次启用流程。
2. 用户可以跳过首次生成，只完成建档和自动设置。
3. 首次多选模块按队列运行，失败不回滚其他成功项。
4. 自动间隔默认 5 楼，可在 1～1000 楼内保存并准确触发。
5. 到期后先执行增量建档判断，再抽模块。
6. 抽签遵守用户排除、近期软冷却、长期公平加权，并在失败恢复时复用原结果。
7. 多请求模块在全部完成前只显示生成壳，不出现信封或成就。
8. 一个完整模块成果只生成一个成就，不因底层调用多次而重复计数。
9. 成就由模块最后一次响应一并返回，不产生额外成就 API。
10. 成就失败时不重做模块、不自动请求；用户确认后的小型修复只补成就。
11. 真实历史使用历史成就，推演／未来／番外成果使用收藏成就，不能混淆正史。
12. 没有新 Mxxx 时不发送第二阶段请求，不生成回忆和成就。
13. 每份成功自动回忆存在对应成就或明确的待补状态。
14. Toast、悬浮信封和楼尾入口打开同一份结果。
15. 楼尾入口不修改聊天正文，也不会发送给模型。
16. 回忆和成就随聊天 metadata 保存。
17. IndexedDB 仅作为恢复备份，不形成第二份可写主档。
18. 成就可跳到有真实聊天楼层的来源；无楼层来源不伪造跳转。
19. 酒馆与 TT 中身份、聊天和档案版本保护保持一致。

## 13. 暂不纳入

- SillyTavern 原生群聊；
- 自动生图；
- 修改或接管兔子镜；
- 把插件生成内容写进聊天正文；
- 通过模型推演解锁真实历史成就；
- 为了达到固定频率伪造 Mxxx；
- 在宿主未公开能力时模拟点击私有界面或读取私有数据库。

## 14. 模块请求次数审计

本节保留审计依据和产品侧成本结论。逐模块的规范生成顺序以 [自动留忆模块生成合同.md](./自动留忆模块生成合同.md) 为准；若后续代码变化导致次数变化，应先更新模块合同，再同步本节摘要。

### 14.1 计数口径

以下数字均指**正常成功路径中的文本生成 HTTP 请求数**，用于：

- 在启用向导中向用户说明大致费用；
- 决定哪些模块适合先开放自动抽签；
- 计算生成壳的阶段进度；
- 约束“一个完整成果对应一个成就”的完成边界。

审计数字不包含：

- 固定周期开始时的增量建档请求；
- 自动生图；
- 网络失败后的人工重试；
- 用户主动重新生成；
- 成就字段异常后由用户确认的小型修复请求。

`requestValidatedSegment()` 的一次正常成功调用等于一次文本 HTTP 请求。当前底层至少保留两次尝试能力，但第二次只会在首轮空响应、无法提取 JSON 或明确允许重试的异常中发生。因此不能把表内所有数字机械乘二；产品界面应显示“正常请求数”，并另行提示“单段异常时可能额外重试一次”。

并发不会减少请求次数。例如三个评论批次即使并行发送，仍然是三次请求。

### 14.2 建档阶段请求数

#### 自动周期中的增量建档

自动周期先完成建档，只有新增出真实 Mxxx 才继续抽模块。

正常请求数近似为：

```text
Cchat + Cexternal

Cchat ≈ ceil(本轮新增聊天字符数 / 30000)
Cexternal ≈ ceil(本轮需要重扫的外部记忆字符数 / 26000)
```

实际分段还会受请求 token 预算影响，因此以上是说明公式，不是计费承诺。

- 用户通常设置 5～10 楼且外部来源未变化时，`Cchat` 通常为 1，`Cexternal` 通常为 0。
- 新增内容为空时应直接结束，不请求模块。
- 外部摘要、世界书记忆来源发生变化时，可能额外产生一个或多个外部分段。
- 增量建档保留现有档案封面，正常情况下不再额外生成档案简介。

#### 第一次建档

第一次建档可能包含：

```text
聊天分段 + 外部记忆分段 + 最终档案简介（通常 0～1 次）
```

长聊天可能被拆成多个可恢复批次，不能在向导中承诺“建档只调用一次 API”。向导应在扫描字数后显示预计分段数，再由用户确认开始。首次建档与首次多选模块队列必须分别计数。

### 14.3 当前模块逐项审计

表中的 `U`、`E`、`S`、`A`、`M`、`B`、`D` 都由本轮计划或待补内容决定：

- `U`：需要生成评论的已解锁相簿条目数；
- `E`：需要生成正文的 ADV 事件数；
- `S`：房间中需要补全的槽位数；
- `A`：电话 App 数或结局可用路线数，按所在行解释；
- `M`：本轮计划更新的电话 App 数；
- `B`：蝴蝶效应分支轴数量；
- `D`：前世今生卷宗数量。

| 模块 | 当前正常请求数 | 当前“完整成果”边界 | 自动化审计结论 |
| --- | ---: | --- | --- |
| 回忆相簿 Album | 仅索引 1；完整为 `2 + ceil(U / 3)` | 索引、关系快照及本轮所有已解锁条目评论都完成 | 不能把只生成索引算成成就；适合第二批接入 |
| ADV | 索引 1；本轮全部正文再加 `ceil(E / 6)`；单篇人工补写每篇加 1 | 本轮索引及其中全部事件正文都完成，只有索引不算完成 | 自动任务必须跑完本轮索引中的全部正文，不能停在目录或只选一篇 |

| 收件箱 Inbox | `0～1` | 有计划时，一次响应中的本轮信件全部完成；无计划为 noop | 第一批；noop 不生成成就或信封 |

| 成就 Achievements | 当前独立 1 | 独立成就列表 | 新方案中移出抽签池；改成各模块最终响应的附属输出 |
| 蝴蝶效应 Butterfly | 首次完整 `2 + B + P`，B 为 1～8，P 为 0～1 次正文补段，即约 3～11；增量通常 1～2 | MAIN、计划分支、Ω 及要求的正文都完成 | 首次生成保留给手动／首次队列；先只开放已有 session 的增量自动生成 |
| 前世今生 Past Lives | 一篇为 `2 + D + P`，D 为 1～6，P 为 0～1 次引子补文，即约 3～9 | 引子、全部卷宗、今生回响与落款完成 | 每次是新 episode 而非档案差量；费用高，放第四批 |
| 主题曲 Theme Song | 每首 1 | 一首完整歌曲成果 | 当前 `automatic: true` 会直接 noop；补齐自动 plan 后才能进入候选 |
| 睡前故事 Bedtime | 每章 1 | 一章完整故事成果 | 当前自动入口 noop，续章还依赖 storyId；需先定义“新故事／续章”规则 |
| 时光回声 Time Echo | 每篇 1 | 一篇完整回声成果 | 当前不在旧自动列表；补自动入口后作为收藏成就进入第二批 |

补充边界：

- 目录、索引、结构草稿和 plan 均为中间状态，本身不能生成成就或信封。
- 多阶段任务必须自动排完本轮剩余步骤；允许受控并发，但不能要求用户逐项点击“继续生成”。
- “完整”以抽签时持久化的本轮计划为准；任务开始后的新聊天不会无限扩展当前计划。
- 房间生活等临时日常状态不等于可归档回忆，除非另行定义不可变成果，否则不进入抽签池。
- 图片生成不计入本方案，也不能阻塞文字成果与成就完成。
- “无新增”“无计划”“容量已满”等可预期 noop 不算成果，不生成信封、不生成成就。
- 某模块已写入部分分段时，恢复必须从未完成分段继续；不得因成就缺失重跑已成功正文。

### 14.4 统一的完整成果合同

每个自动候选必须在模块注册表中声明：

```ts
type AutoMemoryModuleDefinition = {
  id: string;
  title: string;
  description: string;
  contentKind: 'historical' | 'collection';
  normalRequestEstimate: string;
  prerequisites: string[];
  autoEligible: boolean;
  supportsIncremental: boolean;
  achievementMerged: boolean;
  plan(context: unknown): Promise<ModulePlan | null>;
  pendingSteps(result: unknown, plan: ModulePlan): ModuleStep[];
  isComplete(result: unknown, plan: ModulePlan): boolean;
};
```

其中：

- `plan()` 返回 `null` 表示本轮没有可生成内容，不能解锁成就。
- `plan()` 的非空结果必须在首个请求后冻结并持久化；目录型模块要把目录中的全部必需项转为可恢复步骤。
- `pendingSteps()` 决定还需继续生成哪些内容；只要仍有必需步骤，调度器就自动续跑当前模块。
- `isComplete()` 是信封与成就的硬闸门，不能用“请求已经发过”代替。
- `achievementMerged` 只有在模块最终请求已能安全携带成就末包时才为 `true`。
- `autoEligible` 不能由界面勾选直接篡改；它表示代码已经完成适配并通过验收。
- 用户勾选的是偏好；运行候选是“用户已选中 ∩ 前置条件满足 ∩ `autoEligible` ∩ `achievementMerged`”。

由此区分三个概念：

1. **用户喜欢**：默认勾选，可随时排除；
2. **当前可抽**：本轮前置条件满足且存在可生成计划；
3. **工程已开放**：已经具备完整成果合同、恢复机制和成就末包。

向导可以展示全部模块和介绍，但不能让“已选择、尚未适配”的模块看起来正在参与抽签。正式发布时有两种可接受方式：

- 未适配模块显示“暂不可自动生成”，不允许开启；
- 或先不展示该模块的自动开关，待适配版本再出现。

不采用“勾选后静默永远抽不到”的做法。

### 14.5 自动候选分层

建议上线顺序：

1. **第一批低风险**：Cabinet、Calendar、Relations、Inbox。
2. **第二批中等风险**：Travel、Items、Album、Time Echo，以及补好自动 plan 后的 Theme Song、Bedtime。
3. **第三批多阶段样板**：Phone。
4. **第四批目录／树／路线增长模块**：ADV、Ending、Butterfly、Past Lives。
5. **补齐整体计划后加入**：Heart。

Heart 不拆成多个独立成就来规避请求数。接入前需要定义一次模块整体计划，例如明确本轮包含：

- 基础／时期对话；
- 日常一格；
- 萤火虫；
- 后日谈；
- 春、夏、秋、冬各自的 Voice／Scenario 成果。

计划包含的内容全部完成后，Heart 才形成一份回忆和一个成就。若产品未来希望把这些内容变成多个成果，必须先在用户界面中把它们正式定义为可单独勾选、各自有介绍的模块，而不能只在后台偷偷拆分。

ADV 的自动成果是“本轮完整事件集”：先生成索引，再自动生成该索引中的全部事件正文。只有标题的事件索引不算回忆。

最终产品目标仍是让所有已支持自动生成的成果默认选中；上述分层只决定工程何时允许它们真正进入运行时候选，不改变用户可以排除任意模块的产品规则。

```ts
  achievementId: string | null;
  sourceMemoryIds: string[];
  status: 'generating' | 'ready' | 'achievement_pending' | 'opened';
  createdAt: number;
}>
```

本轮只建立 schema、校验、迁移和只读注册表，不改变旧自动更新行为。

验收：

- 老聊天无新字段时保持原行为；
- 新字段损坏时 fail fast 并给出可恢复提示，不静默覆盖；
- interval 只能保存 1～1000；
- metadata 为主档，IndexedDB 恢复副本不能反向覆盖更新版本。

### R1：非阻塞启用向导

建议新增 `src/ui/autoMemoryWizard.js`，复用：

- `participantPicker.js` 的单人卡／多人卡人物确认；
- `overlayCore.requestCurrentArchiveImport()` 的建档能力；
- `taskCenter.enqueueSelectedModes()` 的首次多选队列。

步骤：

1. API 就绪检查；
2. 单人卡／多人卡；
3. 读取范围与外部来源；
4. 模块介绍、正常请求数、排除选择；
5. 自动间隔；
6. 建档预计分段确认；
7. 可跳过的首次生成队列。

向导关闭后任务继续在后台运行，聊天输入不被锁定。向导、任务中心和外置生成壳读取同一任务状态。

验收：

- 可只建档不首次生成；
- 可跳过全部首次生成；
- 多选任务逐项独立成功／失败；
- 刷新后能恢复向导完成状态和后台任务；
- 用户可以正常继续发送与接收聊天。

规则：

- `Achievements` 从旧自动候选中移除，避免模块成就与独立成就重复请求。

验收重点是同一聊天同一楼层只能存在一个自动调度来源。

### R3：统一周期、增量闸门与可恢复抽签

建议新增：

- `src/autoMemory/scheduler.js`
- `src/autoMemory/incrementalGate.js`
- `src/autoMemory/draw.js`

顺序：

1. 到达 `nextDueFloor`；
2. 获取当前聊天调度锁；
3. 执行可分段的增量建档；
4. 没有新 Mxxx 则记录本轮 noop 并计算下一周期；
5. 生成满足前置条件的候选集合；
6. 应用黑名单、近期软冷却和长期公平加权；
7. **先保存抽签票据，再启动模块**；
8. 重试、刷新和恢复必须复用同一票据。

抽签票据至少包含：

```ts
{
  id: string;
  dueFloor: number;
  archiveRevision: string;
  candidates: Array<{ id: string; weight: number }>;
  selectedModuleId: string;
  sourceMemoryIds: string[];
  status: 'drawn' | 'running' | 'completed' | 'failed';
}
```

首版优先使用 Web Locks 防止酒馆与 TT 多实例重复运行；R8 再补 IndexedDB lease fallback。

验收：

- 同一楼层重复事件不重复建档或抽签；
- 刷新后继续相同模块；
- 被排除模块永不进入票据；
- 所有候选均不满足时明确 noop；
- 没有新 Mxxx 时不发模块请求。

补充 IndexedDB 原子 lease，作为缺少 Web Locks 时的后备：

- lease 绑定 chatId、dueFloor、archiveRevision；
- 有短时过期时间和心跳；
- 接管过期 lease 时先检查抽签票据与任务恢复状态；
- 不能仅凭“锁过期”重新发送已成功分段。

全量验收矩阵：

- 酒馆浏览器端与 TT；
- interval 为 1、5、10、1000；
- 新聊天、已有长聊天、切换聊天；

- 建档期间继续聊天；
- 请求中刷新与重开；

- Web Locks 可用与不可用；
- DOM 重绘和楼尾入口重挂载；
- 没有新 Mxxx；
- 模块 noop；

- 外部记忆来源变化；
- 原生 `groupId` 群聊保持明确不支持。

## 16. 审计后的关键结论

1. “每 5～10 楼自动生成一次回忆”至少包含建档与模块两个阶段，不能对用户宣传成固定一次 API。
2. 一个成就必须绑定完整成果，不绑定单次请求；电话首次完整生成可能约 2～11 次请求，但仍只有一个成就。
3. 成就末包不是现有所有模块天然具备的能力，必须逐模块适配后才能开放自动抽签。
4. 自动任务不能停在目录，也不能为了控制费用擅自缩小为单篇或单路线；必须冻结本轮有限计划并自动跑完整体。
5. “所有模块默认勾选”和“所有模块立即可运行”必须分开；前者是用户偏好，后者是工程能力。
6. 第一版应先用四个低风险模块跑通完整闭环，再按 R5a～R5e 扩大候选池。
7. 聊天 metadata 绑定方案可以成立，但必须保留恢复备份、抽签票据和跨实例锁，不能只靠内存状态。
