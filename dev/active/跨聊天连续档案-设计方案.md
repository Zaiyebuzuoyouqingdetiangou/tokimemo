# 跨聊天连续档案 · 设计方案（r84.177 草案，待用户确认后分期实现）

目标：同一剧情换聊天窗口后，**继续使用同一份档案**，而不是把旧档案复制一份。

```
聊天 A ─┐
聊天 B ─┼→ 同一份连续档案（M001…M100 来自 A，M101… 来自 B，之后 C 继续追加）
聊天 C ─┘
```

## 1. 现状

- `src/archive/inheritance.js`：把旧聊天的档案 `clone` 一份，改 `chatId`、生成新的 `archiveRevision`，写进新聊天。结果是 A、B 两份档案以后各自发展，**不符合要求**，不在它的基础上改。
- 档案和已生成内容都存在**各自聊天的元数据**里（`heartbeatMemoriesArchiveV3`、`heartbeatMemoriesTheaterV3`）。插件只能安全地写**当前打开的这个聊天**的元数据；别的聊天只能只读地读出来（档案室里看旧档案就是这样）。
- 现有保护都建立在「档案住在当前聊天元数据里」之上：`archiveRevision` / CAS、删除栅栏、来源证据锚点、聊天身份校验、生命周期保护、独立备份、失败保旧成果。

## 2. 两种做法

### A. 接力（推荐）
一份连续档案有一个「连续档案编号」（lineage）。**任何时刻正式档案只住在一个聊天里**（持有者）。

- 在 B 里选「继续档案 A」：把 A 的正式档案（连同已生成内容）**交接**到 B：编号、`archiveRevision` 链、Mxxx 编号都延续，不产生第二份。B 成为持有者，A 变成只读的「已交给 B 继续」。
- 交接记录放在酒馆扩展设置里的一个小登记表（随酒馆同步到各设备）：lineage → 成员聊天、当前持有者、最新 revision。打开 A 时查表，知道档案已经在 B，只读展示，并提供「接回 A 继续」（再交接一次，按 revision 做 CAS，读到的不是最新就拒绝）。
- 优点：不需要新的存储后端；档案仍住在聊天元数据里，**现有所有保护原样生效**。
- 限制：同一时间只能在一个聊天里继续写；要回 A 写需要点一次「接回」。

### B. 共享存储
正式档案放到酒馆服务器上的一个共享文件里，各聊天只存绑定。

- 优点：A、B、C 可以同时写。
- 缺点：要新写一套存储；酒馆服务器没有原子 CAS，跨设备并发要自己兜；备份、恢复、删除栅栏等都假设档案在聊天元数据里，要大改——**正是要求里「不要为此放宽保护」最容易出事的地方**。

**建议选 A。**

## 3. 按要求逐条对应（做法 A）

1. **用户主动绑定**：只在 B 里由用户从档案室选「继续这份档案」才绑定；不按角色卡、名字、世界书猜。
2. **不是复制**：交接后只有持有者那一份是正式档案；原位置只留只读指针，不再增长。
3. **旧内容不变**：Mxxx、相簿、CG、ADV、心动、结局、邮箱、日历、房间等原样随档案交接，不重新请求、不重新编号。
4. **只追加新历史**：B 的建档 / 增量只读 B 自己的聊天（B 的起始楼层从 1 或用户指定的楼开始），新记忆从 A 的最大编号往后接（M101…）；A 已成功的内容不重做。
5. **保留来源**：每条记忆记录 `sourceChatId` 和楼层 / 证据锚点；档案页上能看到「M050 · 来自聊天 A」「M120 · 来自聊天 B」。覆盖范围按聊天分开记。
6. **不串世界线**：没有登记的聊天照旧「一聊天一档案」。
7. **解绑不毁档**：B 解绑时，把正式档案（含 B 期间新增的记忆，来源仍标 B）交回上一个成员 A，B 回到「没有档案」；不删 A 的内容，不改酒馆原聊天。
8. **B 已有独立档案**：不覆盖、不自动合并。弹出选择：①不继续，保留 B 自己的档案；②先把 B 的档案导出备份，由用户确认后再清空 B、接入连续档案。两边数据都不会被静默改写。

## 4. 保护机制保持不变
- 交接本身是一次「读源 revision → 写目标 → 登记表 CAS 更新持有者 → 源位置写只读指针」的事务；任一步失败，保留旧持有者和旧成果，不出现两份都可写的状态。
- 交接前后都做独立备份。
- 聊天身份校验改为「当前聊天是登记的持有者」；非持有者一律只读。
- 删除栅栏、生命周期保护照旧作用在持有者的档案上。

## 5. 分期
1. 数据：lineage 登记表、记忆来源 `sourceChatId`、按聊天分开的覆盖范围；只读展示来源。不改生成。
2. 绑定与交接：在 B 选「继续档案 A」、B 已有档案时的选择、A 的只读指针与「接回」。
3. 增量：B 的建档 / 自动留忆只读 B 的新楼层并追加。
4. 解绑与多设备同步检查。

每期单独出包、先写测试、真实浏览器里验证交接失败时两边都不坏。

## 6. 需要用户确认
- 换到 B 以后，还会回 A 继续写吗？如果不会，做法 A 最合适；如果会经常 A、B 同时写，需要做法 B（风险和工作量都大很多）。
- B 解绑时，B 期间新增的记忆是否留在连续档案里（建议留下，来源仍标 B）。
